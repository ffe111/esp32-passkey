# ความปลอดภัย / Security notes

ESP32 ไม่มี secure element จึงปลอดภัยน้อยกว่า YubiKey หรือ Titan Key
เหมาะกับการใช้งานส่วนตัว การเรียนรู้ และเป็นคีย์สำรอง ส่วนบัญชีสำคัญมากควรใช้คีย์ที่ผ่านการรับรอง

## สิ่งที่ควรทำ
1. **ตั้ง PIN เสมอ** (`passkey-cli pin set`) ถ้าไม่มี PIN ใครได้บอร์ดไปก็ใช้คีย์ได้ทันที
2. **เปิด flash encryption** สำหรับการใช้งานจริง ถ้าไม่เปิด คนที่ถือบอร์ดสามารถอ่าน flash ออกมาได้
3. ลงทะเบียนคีย์อย่างน้อย 2 ตัวกับบัญชีสำคัญ เผื่อคีย์หาย

## การกดปุ่มยืนยัน (user presence)
- Pico FIDO ต้นฉบับ **ไม่เช็กปุ่ม** จนกว่าจะตั้งค่าผ่าน PicoKey App จึงอนุมัติทุกคำขอเอง โปรแกรมบนคอมสามารถสร้าง passkey หรือใช้ล็อกอินได้เงียบ ๆ
- build ของเราเปิด `FORCE_BUTTON_WAIT` ทุกชิป ต้องกด BOOT ภายใน 30 วินาที
- แก้บั๊ก upstream ที่นับเวลา 15 วินาทีตั้งแต่เริ่มรอ (กดหลังวินาทีที่ 15 จะถูกปฏิเสธทันที) ให้นับจากตอนเริ่มกดแทน
- ESP32 รุ่นแรก: การแตะ touch pad T0 (GPIO4) นับเป็นการกดปุ่มด้วย (`PICOKEYS_TOUCH_PRESENCE`, `firmware/serial-hid/touch_presence.c`) ต้องให้ค่าต่ำกว่า 70% ของค่าอ้างอิงติดกัน 5 ครั้ง สัญญาณรบกวนครั้งเดียวจึงไม่นับ ค่าอ้างอิงลดลงตามสภาพแวดล้อมได้ช้ามาก (ราว 6 วินาที) และไม่ลดเลยเมื่อค่าอยู่ในช่วงที่นิ้วกำลังเข้าใกล้ ถ้ามีคนแตะขาค้างไว้ตอนบูต ค่าอ้างอิงจะต่ำ การแตะจึงไม่นับ (ไม่อนุมัติเอง) จนปล่อยนิ้วแล้วค่าอ้างอิงปรับขึ้นเอง ทดสอบแล้วไม่มีการแตะหลอกเมื่อวางบอร์ดไว้เฉย ๆ แต่ในที่ชื้นหรือมีสายไฟยาวต่ออยู่ควรทดสอบซ้ำ
- ไฟล์ `*_nobutton.bin` ปิดการเช็กปุ่ม ใช้ทดสอบใน QEMU เท่านั้น **ห้ามนำไปใช้จริง** และไม่ถูกแนบใน release

## ความต่างตามรุ่นชิป
| ชิป | ที่เก็บคีย์หลักของอุปกรณ์ (OTP) | หมายเหตุ |
|---|---|---|
| ESP32-S2/S3, C3, C6 | eFuse (โค้ด upstream ของ Pico FIDO) | เฟิร์มแวร์ upstream **เขียน eFuse ตอนบูตครั้งแรก** ซึ่งย้อนกลับไม่ได้ |
| ESP32 (รุ่นแรก) | NVS partition `pk_keys` (0x1F0000) ใน flash (`firmware/serial-hid/otp_esp32_nvs.c`) | ไม่เผา eFuse ย้อนกลับได้ด้วยการ erase flash แต่ปลอดภัยเท่าที่ flash ปลอดภัย จึงควรเปิด flash encryption partition นี้อยู่นอกช่วงที่ไฟล์ .bin เขียน การอัปเดตเฟิร์มแวร์จึงไม่ลบคีย์ ถ้า partition เสีย เฟิร์มแวร์จะไม่สร้างคีย์ใหม่ทับ (กัน passkey เดิมกลายเป็นขยะโดยไม่รู้ตัว) |

## Transport แบบ serial
- ใครที่ต่อสาย USB ได้ก็ส่งคำสั่ง CTAP ได้ แบบเดียวกับ USB key ทั่วไป การกดปุ่ม BOOT ยังเป็นการยืนยันตัวตน (user presence) และ PIN ยังป้องกันอยู่
- โหมดนี้ปิด log ทาง UART0 แล้ว แต่ข้อความบูตจาก ROM ยังออกมาตอน reset ซึ่ง host จะข้ามให้อัตโนมัติ (build `-SerialDebug` เปิด log ไว้ ใช้หาบั๊กเท่านั้น)
- ข้อจำกัดของวงจร auto-reset บนบอร์ด: ขา DTR ของชิป USB-serial ดึง GPIO0 ลงได้ โปรแกรมที่เปิดพอร์ต COM ได้จึง "กดปุ่ม BOOT แทน" ได้ด้วย ปุ่มจึงกันได้แค่การใช้แบบเงียบผ่านเว็บ/แอปทั่วไป ไม่กันมัลแวร์ที่ควบคุมพอร์ต COM โดยตรง (บอร์ด USB ในตัว S2/S3 ไม่มีปัญหานี้)
- ปิดแอป OATH/OTP ไว้ เพราะต้องใช้ CCID หรือคีย์บอร์ด USB
